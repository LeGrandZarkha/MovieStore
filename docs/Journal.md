# Movie Store — Journal de bord

Carnet de travail personnel : notions comprises, bugs rencontrés et raisonnement suivi pour les résoudre, décisions prises en cours de route. Contrairement à `ROADMAP.md`, ce fichier n'est pas destiné à donner une vue d'ensemble propre du projet — c'est une mémoire de travail, à consulter ou compléter au fil des sessions.

## Repères techniques consolidés

- `fetch()` ne rejette jamais sur un code HTTP d'erreur, seulement sur une vraie erreur réseau → toujours vérifier `response.ok`.
- Une donnée calculée à chaque appel (ex: `isNewSearch`, `pageToFetch`) doit être un paramètre de fonction ; un state stable du composant (ex: `setMovies`) peut rester accessible par closure, pas besoin de le passer en paramètre.
- Le débounce ne protège les appels réseau que si l'effet qui déclenche le fetch dépend de la valeur *debouncée* — pas de la valeur brute du state, même si celle-ci est utilisée ailleurs (affichage, filtrage local).
- YAGNI : ne pas complexifier pour un besoin futur hypothétique — question à se poser : "si je me trompe, combien ça coûte de corriger ?" plutôt que "est-ce que ça va changer un jour ?"

## 12/08/2026 — Session design authentification Supabase

Réflexion en amont du code, sur l'architecture auth/favoris. Repères posés, pas encore implémentés.

- **JWT** : le payload est encodé en base64, **pas chiffré** — lisible par quiconque intercepte le token. La signature garantit l'intégrité et l'authenticité du contenu, pas sa confidentialité. Ne jamais mettre de donnée sensible dans le payload.
- **Access token vs refresh token** :
  - Access token : courte durée, utilisé à chaque requête authentifiée.
  - Refresh token : longue durée, stocké côté client (cookie `httpOnly`) ET côté serveur (pour permettre la révocation) — sert à obtenir un nouvel access token sans réauthentification.
  - Vol d'un access token → fenêtre d'exploitation limitée à sa durée de vie (le serveur rejette tout token expiré).
  - Vol d'un refresh token → plus grave, permet de régénérer des access tokens à volonté tant qu'il n'est pas révoqué côté serveur.
- **Callback OAuth** : après redirection vers le provider (GitHub), celui-ci renvoie vers une route dédiée de l'app (`/auth/callback`) — implique que le routing (`react-router-dom`) doit être en place avant l'implémentation OAuth. Parallèle : flow "payer avec PayPal" (redirection externe, puis retour sur la page applicative pertinente, pas la landing page).
- **Context React et re-render** : tout composant consommant un Context re-render dès que n'importe quelle valeur du Context change, même s'il n'en utilise qu'une partie. D'où la séparation `AuthContext` / mécanisme favoris plutôt qu'un seul Context fourre-tout.
- **Optimistic update — vocabulaire à corriger** : c'est un arbitrage UX/cohérence des données, pas une question de "sécurité" (aucune notion de sécurité en jeu dans ce choix).
  Causes réalistes d'échec d'un INSERT : perte réseau côté client, session expirée (refresh silencieux pas encore effectué), violation de contrainte d'unicité (double clic rapide sur le même favori), rate limiting ou indisponibilité momentanée du service.
- **Données périssables vs stockage local** : toute donnée copiée depuis une source externe (ex: objet film TMDB) peut devenir obsolète si la source évolue (note, popularité). Réflexe à généraliser : avant de stocker une copie, se demander si la donnée source peut changer, et ce qu'implique un décalage entre la copie et la réalité au moment de la lecture. Nuance importante : ce raisonnement dépend de la **durée de vie** du stockage — un stockage temporaire (localStorage, quelques jours) tolère mieux la fraîcheur imparfaite qu'un stockage durable (Supabase, potentiellement des mois/années). Une conclusion tranchée dans un contexte ne se généralise pas automatiquement à un autre contexte sans revérifier les prémisses (coût réseau, durée de vie).

## 12/08/2026 — Session design MovieCard, favoris cross-pages, structures de données

- **TMDB n'a pas d'endpoint batch pour récupérer plusieurs films par IDs.** `/find/{external_id}` sert à mapper un ID externe (IMDB) vers TMDB, pas à faire du multi-fetch par IDs TMDB. `/search/multi` est une recherche texte multi-catégories, pas un batch. Un fetch par film est donc obligatoire pour reconstituer une liste de favoris à partir d'IDs seuls — coût à mettre en balance avec le bénéfice de fraîcheur des données selon le contexte de stockage.

- **Séparation des responsabilités dans les composants réutilisables** : un composant comme `MovieCard` ne doit pas aller chercher lui-même son contexte d'usage (ex: `useLocation()` pour savoir sur quelle page il est affiché) — c'est le parent qui doit le lui fournir explicitement via une prop. Un composant testable/réutilisable ne doit pas dépendre implicitement de l'état global de l'app.
  Deux axes de variation indépendants (contexte d'affichage vs état du film) → deux props séparées (`variant` / `isFavorite`), jamais fusionnées.

- **`Set` (structure de données JS)** :
  - Collection de valeurs uniques, sans doublons, sans notion de position/index (contrairement à un tableau).
  - `.has(x)` vérifie une présence en temps quasi-constant (O(1)) via une fonction de hachage : la valeur cherchée est passée dans une formule déterministe qui calcule directement son emplacement de stockage, sans parcourir les autres éléments — contrairement à `array.includes(x)` qui peut parcourir tout le tableau (O(n)).
  - Différent de la recherche par dichotomie (recherche binaire) : la dichotomie nécessite des données **triées** avec accès par **position/index** (couper au milieu, éliminer une moitié) — un `Set` n'a ni ordre exploitable ni accès indexé, donc la dichotomie ne s'y applique pas structurellement.
  - Comme les autres objets JS, un `Set` doit être **remplacé par une nouvelle référence** pour que React détecte un changement dans un `useState` — le modifier en place (`.add()`, `.delete()` sur l'instance existante) ne déclenche pas de re-render.

- **Pourquoi React compare par référence et non par contenu (deep comparison)** : comparer deux objets/tableaux en profondeur à chaque re-render potentiel serait coûteux (parcours récursif de tout le contenu). Comparer deux adresses mémoire est une opération unique et quasi-instantanée, quelle que soit la taille des données. D'où le contrat d'immutabilité : toujours créer une nouvelle référence (spread, `new Set(prev)`) plutôt que muter l'existant.
  Nuance : nouvelle référence déclenche le *recalcul* du composant (re-render), mais React ne réécrit ensuite dans le DOM que ce qui a réellement changé visuellement (réconciliation) — deux étapes distinctes.

- **Cycle de vie de `favoriteIds` (Set des tmdb_id favoris)** : peuplé/vidé via un `useEffect` déclenché par le changement de `user` (pas par un événement de clic précis) — nécessaire pour couvrir à la fois la connexion explicite et la restauration automatique de session (refresh token) au chargement de l'app, qui ne passe pas par un clic. Vidage explicite à la déconnexion (`user` → `null`) pour éviter qu'un Set non vidé ne fasse persister les favoris d'un utilisateur précédent à l'écran.

## 13-14/08/2026 — Session implémentation routing (react-router)

- **`react-router` a plusieurs modes** : declarative, data, framework. Le quickstart officiel (`reactrouter.com/tutorials/quickstart`) pousse par défaut vers le mode **framework** (packages `@react-router/node`, `@react-router/serve`, `isbot`, structure de fichiers imposée, SSR) — pertinent pour une migration depuis Create React App ou un besoin réel de SSR/rendu statique, pas pour un projet Vite existant sans ce besoin. Le mode **declarative** (`npm i react-router` seul, `<BrowserRouter>`/`<Routes>`/`<Route>`) s'ajoute à un projet existant sans rien imposer — c'est celui utilisé ici.
- **`<BrowserRouter>`** : s'installe dans `main.jsx`, englobe `<Routes>` (et tout le reste) — ne remplace pas le composant racine, il active seulement le mécanisme de routing (accès à l'URL/historique).
- **`<StrictMode>`** : outil de détection de bugs en dev uniquement (aucun effet en prod). Monte/démonte/remonte les composants une fois de plus qu'attendu et exécute deux fois certaines fonctions (corps de composant, `useEffect`) pour révéler des effets de bord mal nettoyés. Doit englober **tout** le reste, y compris `BrowserRouter` — un outil de surveillance globale doit être le plus extérieur possible dans l'arbre, sinon il laisse un angle mort sur ce qu'il ne recouvre pas. Un double fetch visible en dev avec StrictMode actif est un signal à corriger (effet mal géré), pas une raison de désactiver StrictMode.
- **Nested routes et `<Outlet />`** : une route parente (`<Route element={<Layout />}>`) englobe des routes enfants ; le parent doit contenir explicitement `<Outlet />` à l'endroit où le contenu de la route enfant active doit s'afficher. Sans `<Outlet />`, l'URL change mais rien ne s'affiche. Usage principal identifié ici : **layout partagé** (nav commune visible sur toutes les pages), pas hiérarchie de contenu — `Layout.jsx` comme route parente sans `path` propre, `Discovery`/`Favorites` comme enfants rendus via `<Outlet />`.
- **`<Link>` vs `<button onClick={...}>`** : `<Link to="...">` change l'URL de l'app suite à un clic utilisateur volontaire (navigation interne) — nécessite un `to` valide, ne peut pas déclencher de JS arbitraire ni de redirection externe. `<button onClick={...}>` déclenche du code (ouvrir une modale, appeler une fonction) sans changer l'URL. Un bouton de connexion qui doit ouvrir une modale de choix de provider est un `<button>`, jamais un `<Link>` — même mal formé, un `<Link>` reste conceptuellement le mauvais outil ici.
- **Route `/AuthCallback` (future `/auth/callback`) : ne doit jamais apparaître dans la nav.** Elle n'est atteinte que par la redirection **de GitHub** après authentification côté GitHub — jamais par un clic interne à l'app. Séquence complète : clic sur "GitHub" dans la modale → `supabase.auth.signInWithOAuth(...)` → redirection vers github.com (l'app est quittée) → autorisation côté GitHub → redirection de GitHub vers l'URL de callback préconfigurée → traitement de la session côté app → redirection programmatique (`useNavigate()`, pas `<Link>`) vers `/`.
- **Convention de commit affinée** : une dépendance ajoutée (`package.json`) est regroupée dans le même commit que sa première utilisation réelle — un commit "dépendance seule" ne se suffit pas à lui-même en tant que changement cohérent. Un message de commit décrit ce que le commit fait, pas ce qui reste à faire ou pourquoi une future étape est nécessaire — ce rôle revient au Roadmap (sections "Prochaines étapes"/"Points ouverts"), pour éviter deux sources de vérité à synchroniser.
- **Renommage de fichier référencé ailleurs (`App.jsx` → `Discovery.jsx`)** : un commit "isolé" ne veut pas dire "un seul fichier modifié" mais "une seule intention" — un renommage touche mécaniquement tous les fichiers qui référencent l'ancien nom (ici `main.jsx`), et ils appartiennent au même commit. Ce qui casserait l'isolation serait de mélanger, dans ce commit, des changements sans lien avec le renommage lui-même.
